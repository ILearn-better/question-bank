# 笔记的备份与迁移

> 需求提出：2026-09-28。**状态：已实现**。用户原话：「笔记要能够进行备份、迁移。
> 后续可以将迁移文件给其他设备。」

## 0. 一句话结论

「备份 / 迁移」按钮在笔记页左栏，导出**一个 zip**；在新设备上装好拾课、打开同一个地方、
导入这个包即可。目录结构、正文、板书笔画、正文里的配图全都跟着走。

```
笔记页 → 备份 / 迁移 → [导出全部笔记（共 5 篇）]      →  拾课笔记备份_20260928_1430.zip
                    → [选择备份包 .zip] [先试算] [开始导入]
```

## 1. 为什么是一个 zip，而不是「导出一堆 .md」

笔记**不只是文本**：还有目录归属、同一目录里的手排顺序、置顶、板书笔画（矢量 JSON 的
`ink`）、正文里嵌的配图。只导 `.md` 的话这些都丢了，导回来是一堆平铺的散文件 ——
目录得重排、板书没了、图全断。

但**包里仍然放了一份人可读的 `.md`**（机器导入其实只看 `notes.json`）：

> 备份要能活过这个程序本身。哪天拾课跑不起来了，把 zip 解开丢进资源管理器，
> 照样能按目录把每一篇读出来。

这和「作业原件改名成 `学生_日期_序号`」是同一个用意：**存下来的东西应当脱离程序也能自证、能读**。

## 2. 包结构

```
manifest.json                     格式与版本、导出时间、数量、涉及的体系（按 code）
notes.json                        机器导入用：目录记录 + 每篇的完整数据 + 引用到的配图名
notes/<体系>/<目录…>/<标题>.md     人看的副本（正文 + 一行来源说明）
目录树.md                          一页纸的目录总览
images/                           正文引用到的配图原文件
```

同名笔记/目录在包里会自动加「 2」，不互相盖掉。包的格式有 `version`，
导入时**高版本直接拒绝**并说明原因 —— 与其猜着读一半，不如让用户先升级程序。

## 3. 导入的三条规矩

### 3.1 目录按**名字**合并

同一个体系下同名目录就当同一个（复用），缺哪级建哪级。于是**同一个包导入两次
不会长出两套目录** —— 这条很关键：迁移时用户很可能不确定导没导过，会再导一次。

### 3.2 体系按 `code` 认，**不按 id**

另一台设备上 `curricula.id` 不一定一样（甚至是 db 重建过的），但 `code`
（`dse-math` / `cn-junior-math` 这类）是稳定的。实测：全新安装的库里
`[拾课] 初始化：新增体系 4 个` —— 四个体系的 code 与本机一致，所以归属能对上。

认不出来的体系**不拒绝整包**：相关笔记落到「未归档」+ 给一条警告写在报告里。
一个体系对不上就整包退回，是最容易把人卡死的做法。

### 3.3 笔记 id 相同 = 同一篇，默认**跳过**

默认保留本机那份。要覆盖得显式勾选（或 `?overwrite=true`）。
理由：迁移场景下「id 相同」恰恰说明两边同源，而覆盖可能无声盖掉本机较新的内容；
反过来，本机那份要是旧的，用户勾一下覆盖就行 —— **默认值应该选那个不容易后悔的**。

导入还有 `?dry_run=true`：只算不写，报告里会说「会新建几篇、跳过几篇、建几个目录」。
界面上就是「先试算（不写入）」那个按钮 —— 面对「会不会把我的东西盖掉」这种担心，
能先问一遍比事后解释便宜得多。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/notes-backup/export` | 导出全部笔记为一个 zip |
| POST | `/api/notes-backup/import` | 导入包；`?overwrite=` / `?dry_run=` |

⚠️ 前缀特意用 `/api/notes-backup` 而不是 `/api/notes/backup`：
`/api/notes/{nid}/export` 和 `/api/notes/backup/export` 都是「两段路径」，
靠路由注册顺序才能分清楚 —— 那种依赖迟早被一次重构踩坏（笔记树那次已经踩过：
`/api/notes/tree` 会被 `/api/notes/{nid}` 抢走）。换个前缀就完全没有这个问题。

导入报告长这样（界面直接把它摊开给用户看）：

```json
{"notes_created": 6, "notes_overwritten": 0, "notes_skipped": 0, "notes_total": 6,
 "folders_created": 2, "folders_reused": 1,
 "images_added": 1, "images_skipped": 0,
 "warnings": ["备份里的体系「nope-sys」这台设备上没有，相关笔记放进了「未归档」"]}
```

## 5. 边界与安全

- **配图按魔数校验、只取 basename**：包里带 `../` 的文件名一律不认（和上传配图同一套规矩）。
- 包大小上限 300MB（正常几 MB），读完即止。
- 导入全程一个事务，出错整体回滚 —— 不允许「建了一半目录」这种中间态。
- **这个包只装笔记**。学生、课时、反馈、作业不在里面（那是另一个量级的事，
  真要整库搬家应该连 `shike.db` 一起拷 —— 设置页的手工备份做的是那件事）。

## 6. 验证

`backend/test_notes_transfer.py`（44 项断言）：
从**真库只读导出** → 导进一个**独立的临时库**（自己的 DB + 自己的 uploads，
`SHIKE_DATA_DIR`/`SHIKE_DB_PATH` 都指到临时目录）→ 检查 id/标题/体系归属/目录层级
与真库完全一致 → 再导一次（全部跳过、数量不变）→ 覆盖模式（全部覆盖）→
造一篇**带配图 + 板书**的笔记、导出、清空临时库、再导入（配图与笔画都回来、
接口能取到图）→ 坏包 / 别的程序的包 / 更高版本的包一律 422 且原因说得清 →
包里有个本机没有的体系时落到未归档 + 警告。

浏览器点击也走了一遍：弹窗、按钮禁用态、试算报告、真导入（导的是本机自己的包 →
报告「新建 0、跳过 5」）、导出（200 + `application/zip` + 成功提示）。
**全程没有写用户数据**：导入用的是本机自己导出的包（同 id 全部跳过）。

## 7. 没做的

- **按目录导出**（只导「DSE 数学」这一支）：现在只能全量。真需要再加一个 `?folder_id=`。
- **增量 / 自动备份到某个目录**：现在是「用户想起来点一下」。真要自动化，
  应该在设置页配一个「每次退出时导出到某文件夹」，比藏在笔记页里合适。
- **打包学生 / 课时 / 反馈**：不在这个包的范围里（见 §5）。
