# 拾课 · 项目优化建议（2026-10-26）

> 做法：1 个主控（监督）+ 2 个只读审计 agent（后端 / 前端）并行排查，
> **所有条目都要求给 `文件:行号` 证据**；主控对 P0/P1 逐条复核过代码，
> 标 ✅ 的是我自己打开文件核对过的，未标的是审计报告里有行号但我没重读的。
>
> 项目现状：后端约 2.64 万行、前端约 1.74 万行、39 个后端测试 + 13 个前端静态检查。
> 数据库 3MB / 265 道题，`data/` 共 283MB（631 个上传文件）。

## 一句话结论

**功能层面已经相当完整，主要风险不在「还能做什么」，而在「已有的东西会不会悄悄坏」**：
一是备份只备了 3MB 的库、没备 283MB 的图，且没有恢复入口；
二是公式渲染上一轮只修了 1/3 的页面，另外两个大页面还在旧管线；
三是几处「先删再算」的流程，失败时会连上一次的好结果一起删掉。

按这三条修，收益最大；其余是让改动更省事的长线整理。

## 二、P0：先修这三条

### 1. 备份只备了库，没备图；而且没有「恢复」

**证据**
- `backend/app/migrate.py:25` `backup_db()` 只对 `config.DB_PATH` 做 `src.backup(out)`。
- `backend/app/routers/system.py:72` 只有 `POST /api/system/backup`；同文件 `:85` 只有 `GET /api/system/backups`（列清单）。**全项目没有 restore 端点**（`notes_transfer.py:419` 的导入只针对笔记 zip）。
- 实测：`questions` 265 道，其中 `image` 非空 38 道、`figure_image` 非空 123 道 → **161 道（61%）的呈现依赖 `data/uploads` 里的文件**；另有 284 条 `batch_items` 配图。

**后果**
库是 3MB、图是 280MB。把备份拷到另一台机器，打开后题目都在、图全 404 ——
出卷印不出来、批改看不到卷面。而且因为「备份」二字看着很完备，这个洞不会被发现，直到真的要用。

**建议改法**
1. `backup_db()` 里追加一份 `uploads` 的清单校验（不必每次全量拷 280MB），
   外加一个「完整打包」入口 `POST /api/system/backup-full`：DB + uploads 打成一个 zip，
   复用 `notes_transfer.py` 已有的 zip 写法。
2. 加 `POST /api/system/restore`：先从上传的 zip 校验结构（`shike.db` 必须存在、
   `uploads/` 条目数对得上），再**备份当前库**，然后覆盖；整个过程放在一个事务里，
   出错就整体回滚。⚠️ 恢复是危险操作，接口层面要求显式 `confirm: true`。
3. 设置页加一行提示：「备份 = 库 + 图片，共约 283MB」。

**成本** M（约半天）

### 2. 公式保护上一轮只修了 1/3 的页面（我自己的遗漏）

**证据**（`grep -c protectMath`）

| 页面 | 保护 | 实际实现 |
|---|---|---|
| `index.html`（SPA） | ✅ 走 `src/mathRender.js` | 有 |
| `entry.html` | ✅ 4 处 | 有 |
| `batch.html` | ❌ 0 处 | `:980` `marked.parse(normalizeMath(t), …)` |
| `workbench.html` | ❌ 0 处 | `:3371` `marked.parse(md)` |

**后果**
上一轮「AI 转 Markdown 渲染失败」的修法只落在录题页和 SPA 上。
**整页识别的待审页（`batch.html`）和批改工作台（`workbench.html`）仍然是旧管线**——
`$S=2*3*4$` 会被 marked 变成 `$S=2<em>3</em>4$`，`%`、`{`、`&`、`~~` 全部照旧坏。
也就是说老师在待审页看 AI 识别出来的答案，公式还是碎的。

**建议改法**
把 `protectMath` / `restoreMath` 从 `entry.html` 里那份抄到 `batch.html`、`workbench.html`
（零构建页不能 import ES 模块，只能复制；`workbench.html` 已有 `// mirror` 注释的同类做法可循）。
再把 `math_render_check.js` 的覆盖从 2 份扩到 4 份，用**行为对比**守住——
否则下次改动又会漏掉某一份。

**成本** S（1~2 小时）

### 3. 重新批改先删旧结果，失败就全丢

**证据**
`backend/app/services/grade_store.py:1900`
```python
# 重跑：旧题全清（连同挂在上面的标注）。
db.execute(delete(HomeworkGradeItem).where(HomeworkGradeItem.grade_id == gid))
db.commit()
```
删完立刻 `commit`，然后才去读框、起线程跑 AI。

**后果**
老师对一份作业重跑，只要中途 AI 报错、进程被杀、或断电，**上一次的逐题判定全没了**，
连挂在题上的框和标注一起没。而且 `grade.status` 还可能留在 `running`（见 P1-6），
给人「还在跑」的错觉。

**建议改法**
不删旧结果，给 `HomeworkGradeItem` 加 `run_no`（或直接用 `grade.runs` 计数），
新一轮写入 `run_no+1`，全部成功后再删旧 `run_no` 的行；失败则保留旧的一轮。
最小改法（不改表）：先把旧行打成「归档」标记再算，成功后再物理删。

**成本** S~M

## 三、P1：影响体验与稳定

### 4. `async def` 上传路由里做同步 CPU 重活 ✅核实
- `routers/documents.py:232` `async def upload_document` → `:241` `register_document(...)`：当场解析 docx/pdf 全部块。**← 这类才是真重活**
- ⚠️ **勘误（2026-10-27）**：本条原来把 `routers/uploads.py:32` `upload_image` → `images.save_image(...)`
  写成「PIL 解码 + PNG 重编码，几百毫秒到数秒」，**是错的**。`save_image` 只做魔数嗅探
  `sniff_ext()` + `Path.write_bytes()`，**纯转手，没有任何 PIL 解码/重编码**（`services/images.py`）。
  这个端点改 `def` 是为了统一口径（省得以后有人往上传路径里加压缩），**不是因为慢**。
  真正的重活在别处：`register_document` 的 PyMuPDF / python-docx 解析、`.docx` 转 PDF 的 Word COM、
  批改里裁图与整页识别的 PIL —— 这几条才是必须挪出事件循环的。
- 另有 8 个 `async def` 上传端点（`exams.py:389`、`feedbacks.py:471`、`grade_archives.py:82`、`homework_grades.py:200`、`lesson_files.py:142`、`notes.py:268`/`:294`、`plans.py:443`）。

**后果** 单人用不会崩，但「上传大 PDF 时页面其他请求全部排队」是可感知的卡顿。
**改法** 最省事：把这几个 `async def` 改成同步 `def`，FastAPI 自动丢进线程池（改动只有 `async`→删掉 + 去掉 `await file.read()` 改 `file.file.read()`）。
**成本** S

### 5. 批改留存从不回收 ✅核实
`data/uploads/grades` = **167MB / 27 份**，没有任何清理入口；`grade_store.py` 里没有按数量或时间的回收逻辑。
**改法** 设置页加「批改存档保留份数」（默认 20），超出的从最旧开始删，删前同样先算引用。
**成本** M

### 6. AI 失败时状态可能停在 `running`
`grade_store.py:1792` `_running: set[int]`、`:1888` `grade.status = "running"`；
`:1828` 靠「本进程里真有这个线程」判断僵尸，但进程重启后判断依据就没了。
**后果** 界面一直转圈，用户只能重启服务。
**建议** 加 `heartbeat_at` 列，超时（如 10 分钟无心跳）自动转 `failed` 并写明原因。
**成本** S

### 7. 单页识别失败仍会整批入库
`services/batch_page.py` 里页级结果里失败页只有标记，`approve` 流程不因它中止。
**后果** 一批 44 页里有 3 页识别失败，入库后少了 3 页的题，但没有任何提示。
**建议** `approve` 前统计失败页数，>0 时返回「可入库但缺 N 页」并要求前端二次确认。
**成本** S

### 8. 录题页拉全库题目再前端过滤 ✅核实
`frontend/entry.html:1305` `const qs = await this.api('/api/questions');`
→ `:1306` 有 doc 时前端 `filter(q => q.document_id === this.doc.id)`。
**后果** 265 道题时无感；题库到两三千道时，录题页每次加载都要传整个题库。
**改法** 改用已有分页参数：`/api/questions?document_id=…`，无 doc 时只取最近 N 条。
**成本** S

### 9. 两个内存缓存无上界
`attendance_cache`、`students_cache` 只增不减（审计报告指出，未复核）。
**改法** 换 `functools.lru_cache(maxsize=256)` 或加时间戳淘汰。
**成本** S

## 四、P2：该修但能忍

### 10. 删文档靠字符串匹配找孤儿文件
按 URL 前缀匹配找「没人引用的文件」，路径写法一改（相对/绝对、前缀不同）就漏删。
**改法** 统一用 `config.abs_path()` / `rel_path()` 归一化后再比；或维护引用表。
**成本** M

### 11. 循环里逐条查库（N+1）
`students.py:211 student_timeline` 等处在 for 里查库。**改法** 先收集 id 一次 `in_()` 查回。
**成本** S

### 12. `models.py` 1568 行 / `schemas.py` 943 行
**改法** 按域拆成 `models/question.py`、`models/grade.py`… 用 `models/__init__.py` 重导出，
SQLAlchemy 关系不受影响（拆的时候注意 `relationship` 用字符串引用，别改成 import 循环）。
**成本** M

### 13. 请求封装有 4 份 ✅核实
`workbench.html:1754`、`batch.html:1168`、`entry.html:1163` 各有一份逐字相同的 `async api(url, opt)`，
`src/api.js` 是 SPA 那份 —— 错误提示一改就要改 4 处。
**改法** 抽一个 `src/apiLite.js`（普通脚本，挂 `window.ShikeApi`），
三个零构建页 `<script src>` 引入；SPA 继续用 ES 模块版，但内部实现调用同一份。
**成本** S

### 14. 两套批改台并存 ✅核实
`workbench.html`（3471 行，标题「批改工作台」，`src/backTarget.js:6` 称「新版」）
与 SPA 的 `/#/grade/:id`（`src/views/HomeworkGrade.js` 2122 行，代码里自称「旧版批改台」）。
两套都在入口可达（`src/App.js:48` 链新、`src/views/Dashboard.js:79` 链旧）。
**后果** 同类 bug 要修两遍，行为还容易不一致。
**建议** 先明确「旧版是否还有人用」；不用就在 Dashboard 摘掉入口、加一行注释说明保留原因，别再慢慢分叉。
**成本** L（删）／S（只摘入口）

### 15. 231 处行内 `style=` ✅核实
`workbench.html` 63、`batch.html` 79、`entry.html` 89。
主题色/间距散在模板里，改一次要在三处找。
**改法** 增量治理：只把「重复出现 ≥3 次」的抽成 `app.css` 的类（如 `.panel-hint`、`.toolbar`），
不追求一次清完。
**成本** M

### 16. 备份目录留下 WAL 孤儿 ✅核实
`migrate.py:57` `glob("shike-*.db")` 匹配不到 `.db-shm` / `.db-wal`。
实测 `data/backups/`：12 个 `.db` + **12 个 `.db-shm` + 12 个 `.db-wal`**。
**改法** 清理时同时 `glob("shike-*.db*")`；备份完成后对目标执行 `PRAGMA journal_mode=DELETE`，
从根上不产生 sidecar。
**成本** S

### 17. `JSON.parse` 缺保护 / `return await` 冗余
前端 `JSON.parse` 直接调用（一条坏数据整页打不开）；后端多处 `return await x()` 无 try 意义。
**改法** 前端统一 `safeJson(v, fallback)`；后端去掉无意义的 `return await`。
**成本** S
