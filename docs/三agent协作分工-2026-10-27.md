## 一、为什么是「1 修复 + 1 测试 + 1 技能」，而不是 3 个一起改

修复和验证如果由同一个 agent 做，会有两个必然的坏结果：

1. **自己写测试证明自己没写错**。它知道自己的实现细节，测试会不自觉地贴着实现写，
   改坏了也能过 —— 这是「假绿」。
2. **没有人能说清「修好了」的判据**。都自己说了算，最后只能看代码像不像对。

所以拆成三方，用**「先红后绿」**把判断权交出去：

```
tester 先写出「现在一定失败」的测试 → fixer 让它变绿 → tester 独立验绿 + 跑全量回归
```

这是本项目已经吃过亏的纪律：上一轮公式渲染修复时，`protectMath` 被改成空操作，
测试立刻报 15 条 FAIL —— 就是因为测试是独立写的、没贴着实现写。

第三个 agent 做 skill 拆解，与修复**没有任何文件交集**，全程并行，不参与阶段门。

修 P0 的时候顺手重构邻近代码，是这一轮最该避免的事（一改就说不清是哪个改动生效）。

### R1（P0）公式占位符保护补齐到 4 个页面

| `workbench.html:3371` | ❌ `marked.parse(md)` | 同上 |

- 零构建页不能 `import`，只能复制；**复制后必须与 `entry.html` 那份逐字同逻辑**。

### R2（P0）重新批改不再先删旧结果

`backend/app/services/grade_store.py:1900` 现在：
```python
# 重跑：旧题全清（连同挂在上面的标注）。
db.execute(delete(HomeworkGradeItem).where(HomeworkGradeItem.grade_id == gid))
db.commit()
```
删完立刻 commit，之后才起线程跑 AI —— 中途失败 = 上一次批改连同标注全没。

- 目标：**新一轮全部成功后才删旧行**；失败保留旧一轮。
- 允许的最小改法（不改表结构）：先把旧行标记归档 / 或先按 `run_no` 隔离写入，成功后删旧。
- **另加一道门**：`grade.status == "done"` 或 `reviewed_at` 非空时，重跑要求显式确认
  （接口层 409 + 说明「会清掉逐题复核与批注」）。这一条 tester 会用接口测试守。

### R3（P1）上传路由去掉 `async`，别堵事件循环

`async def` 里做同步 CPU 重活（Word COM 导出 PDF、PyMuPDF / python-docx 当场解析）→ 单进程服务整站卡住。

⚠️ **勘误（2026-10-27）**：本节原先把「PIL 重编码」也列成重活，**是错的** ——
`images.save_image()` 只做 `sniff_ext()` + `write_bytes()`，纯转手，没有 PIL。
`uploads.upload_image` 那条**为统一口径而改，不是因为它慢**；判断某端点该不该改，
看的是「里面有没有同步解析/转换」，不是「有没有图片」。

- 改法：`async def` → `def`，`await file.read(n)` → `file.file.read(n)`。
- 只改确有同步重活的那几个（`documents.py:232`、`notes.py:294`、`uploads.py:32`、
  `lesson_files.py:142`、`homework_grades.py:200`、`grade_archives.py:82` 等），
  纯 `await file.read()` 转手的小端点不必动。
- ⚠️ 改完必须逐个回归上传，**这是最容易被改坏的一处**（`file.file` vs `file`、依赖注入顺序）。

### R4（P1）录题页拉题改用 `document_id` 过滤

`frontend/entry.html:1305` 现在拉全库再前端 `filter`。后端 `GET /api/questions?document_id=` 已支持。

- 改法：有 doc 时带参数、删掉前端过滤；无 doc 时只取最近 N 条。
- 判据：tester 验「有 doc 时请求 URL 带 document_id」「列表内容仍正确」。

## 五、skill 拆解：3 个 skill 的边界与输入输出

目标不是「把接口再写一遍文档」，而是**让 agent 拿到一句话就能做事**：
识别意图 → 检查服务 → 调对接口 → 轮询 → 用人的语言报告。
每个 skill 都要写清「什么时候用我 / 什么时候别用我」，这是最容易含糊、也最影响调用准确率的部分。

### Skill 1：`shike-ingest`（讲义 / 试卷自动入库）

| 项 | 内容 |
|---|---|
| **触发** | 「把这份讲义录进题库」「这个 PDF 入库」「上传这份卷子，入完告诉我」 |
| **不触发** | 只想知道某道题在不在库里；只想看文件内容；要出卷（→ `shike-paper`） |
| **输入** | ① 文件路径（**必需**，本机绝对路径）② 体系 curriculum（**必需**，不认识就问人，不许猜）③ 页范围（可选） |
| **输出** | 结构化报告：`{total, approved, needs_human, skipped, task_id, 需人工清单[{页, 题, 原因, 审核链接}]}` |
| **后端** | `POST /api/auto/import-path` → `GET /api/auto/imports/{id}` 轮询 → `POST .../resume` |
| **关键纪律** | 体系**绝不自动猜**（猜错整批知识点挂错树，且不报错，只在出卷时才发现）；一份 44 页约 30 分钟，**不能用短超时**；退出码 0/2/1 三种结局必须分别报告 |

### Skill 2：`shike-paper`（组卷 / 出讲义）

| 项 | 内容 |
|---|---|
| **触发** | 「按这份要求组一份试卷」「找 10 道导数题出一张卷子」「做一份讲义，包含…」 |
| **不触发** | 只要题目清单不出卷（直接查 `/api/questions` 即可）；要录入新题（→ `shike-ingest`） |
| **输入** | ① 组卷要求：知识点 / 难度 / 题数 / 题型 / 考试用途 ② 输出格式（html / docx / pdf）③ 模板（可选） |
| **输出** | ① 候选题目清单（含 id、题干摘要、知识点、难度）② 确认后导出文件路径 / 预览链接 |
| **后端** | `GET /api/questions/search`（按知识点/标签/难度检索）→ `GET /api/papers/export?ids=…&format=…`；模板 `GET /api/paper-templates` |
| **关键纪律** | **先给清单让人确认，再导出** —— 组卷是「选哪些题」，替用户决定就会印错卷；题量不够时如实说少几道，不许拿相近题凑数 |

### Skill 3：`shike-doc`（文档处理：转 Markdown）

| 项 | 内容 |
|---|---|
| **触发** | 「把这个 docx 转成 markdown」「这份 PDF 的文字提出来」 |
| **不触发** | 要入库成题（→ `shike-ingest`）；要进题库笔记且需要保留原件（走笔记导入，skill 里说明区别） |
| **输入** | 文件路径 + 目标（只看内容 / 存成 .md 文件 / 存成拾课笔记） |
| **输出** | Markdown 文本或落盘路径 + **失真与警告**（转换丢失了什么必须说，不能只报成功） |
| **后端** | `POST /api/notes/import-doc`（转成笔记，带原件）；纯文本提取走 `services/file_text` |
| **关键纪律** | 转出来一定附「哪些没转好」；**公式与表格是重点**（电子版 PDF 的文字层对公式是废的，需要视觉模型，skill 里必须写明这个边界） |

### skill 放在哪里

`question-bank/.workbuddy/skills/<name>/SKILL.md` —— **项目级**，跟着仓库走，
两台机器共享，与接口版本同生共死。不放用户级：这三个 skill 强绑定本项目的端口约定
（目录名含 `question-bank-ai` → 8010，否则 8000）和接口形状，换个项目就没意义。

## 六、全员必须遵守的技术纪律（本项目踩过的坑）

1. **端口按检出目录名**：`question-bank-ai` → 8010，否则 → 8000；`SHIKE_BASE` 可覆盖。写死任一个 = 假通过。
   ⚠️ **但有一条不能对这个规则**：9 个测试写死 **8001**（`doc_import / feedback_course / note_groups /
   note_questions / notes_transfer / prep / question_filters / supplements` + `test_upload_runtime`），
   因为它们是**写入型**用例（建学生/课时/备课/笔记/作业），8001 是自带独立 DB 的临时服（见 `test_prep.py` 文件头）。
   **把它们「对齐」到 8000/8010 就是让它们去改老师的真库** —— 那是不可恢复的事故，不是红绿问题。
   默认保持 8001，只允许 `SHIKE_SCRATCH` 显式覆盖。
1b. **测试一律从 `backend/` 目录跑**。在仓库根跑，alembic 的 `script_location` 按 CWD 解析，
    找不到 `alembic/versions` 会直接炸迁移 —— 而它炸的样子很像「迁移丢了」或「测试写坏了」，
    是会让人白改一遍代码的假信号。例外：`启动拾课.bat` 在仓库根跑。
2. **本机 shell 带 `http_proxy`** → `urllib` 探 `127.0.0.1` 会被送进代理返 **502**（看着像服务坏了）。
   测试必须 `build_opener(ProxyHandler({}))`；Edge 加 `--no-proxy-server`。
3. **agent 起的服务活不长**。验证要么用临时库直调函数（不起服务），要么明确告诉用户「双击 `启动拾课.bat`」。
4. **测试脚本自包含**：`check(name, ok, detail)` + `fails`，`sys.exit(main())`，退出码即结果。
   ⚠️ 别用管道取 `$?`（那是 `tail` 的码）→ `>log 2>&1; echo $?`。
5. **会写真库的测试**：快照 → 动作 → `finally` 还原；清理**只锚不可变 id**，
   **绝不「删库里所有题目/所有课」**（误删过用户刚录的题）。
6. **反面断言看代码不看注释**（`codeOnly()`）；**正面断言验「用户看得见的结果」**。
6b. **用脚本批量改测试文件后，必须跑一次 AST 自检**：每个新插入的定义，**行号必须小于首次使用行号**。
    踩过：按「最后一条顶层 import」定位插 `_OPENER`，在某个文件里匹配到了 `import pymupdf`（第 124 行），
    定义被挪到第 127 行，而第 42 行就用了 → `NameError`。**而 `NameError` 长得跟「改动把功能弄坏了」一模一样**，
    会让人回头改业务代码。
6c. **别用 bash heredoc 把 Python 灌进 `python -c` 去改文件**：MSYS 会把字符串里的 `\n` 转成 `/n`，
    于是 `if skipped:\n    print(...)` 变成一行 → `SyntaxError`，看起来像「把文件改坏了」。
    要改文件就**写一个 .py 再执行**，别走 heredoc。
6d. **读别人的文件前先看 mtime**：mtime 距现在不足 2 秒的，可能是写到一半，**不下结论、不报缺陷**。
    本轮三个人各踩过一次（把中间态读成「漏改了」/「有 NameError」）。
7. **破坏性验证**：断言写完要把实现改坏一次，确认断言真能抓到（且能区分「断言抓到」与「代码炸了」）。
8. **in-DOM 模板**：`/>` 不自闭合 → 整页白屏；模板字面量里不许有反引号；CSS 注释必须配平。
9. **公式必须先占位符保护再进 marked**（就是 R1 这件事本身）。
10. 改后端后**强制重启**再验；前端不用（Ctrl+F5）。
11. 第三方库脚本用 `backend/.venv/Scripts/python.exe`；node 用
    `C:/Users/6/.workbuddy/binaries/node/versions/22.22.2-6/node.exe`；`node --check` 只认 stdin。
12. **不 commit、不 push**。改动留在工作区，主控汇总后等用户确认。

## 七、什么算「做完」

| Agent | 交付标准 |
|---|---|

| skill-smith | ① 3 个 `SKILL.md` 各自可独立调用 ② 每个都写明「何时用/何时别用/输入/输出/失败怎么报」 ③ 用真实接口跑通至少一条（或明确标注「未跑通，需要服务在跑」） |
