# 拾课（shike） · 独立教师教学管理系统 · 调研与开发文档

> 版本：v1.4 | 日期：2026-09-20 | 基线代码：`question-bank`（commit 见仓库，Phase 0 改名 `shike`）
> 项目定名：**拾课**（英文标识 `shike`，2026-09-20 确认，见附录 C）
> 场景：独立数学教师自用 · 多体系（DSE / A-Level / 国内初中 / 国内高中 / 后续体系）· 单人操作 · 本地部署

## 0. 定位与结论

### 0.1 产品定位（v1.1 明确）

**这是一个「学生情况管理工具」，不是题库系统，也不是教务系统。**

核心价值一句话：**把「学生规划、学生情况记录、家长可视化」这三件事，从脑子里和零散的聊天记录里搬进一个能自动沉淀、自动成图的系统，解放自己的精力。**

由此推出三条定位原则：

| 原则 | 含义 | 直接后果 |
|------|------|---------|
| **记录优先于功能** | 系统的第一价值是"记得下来"，不是"功能多" | 录入必须极快（≤3 分钟/节课）。任何需要填十几个字段的设计都算失败 |
| **学生为中心，题库为燃料** | 题目和知识点不是目的，是"诊断与规划"的原材料 | 模块①降级为支撑设施；组卷/排版/试卷导出等"对外交付"能力后置甚至砍掉 |
| **家长可视化是价值出口** | 记录完之后，系统必须产出家长看得懂的东西 | 家长报告**不依赖题库**（用老师主观评分即可起步），因此可大幅提前 |

### 0.1.1 两阶段定位（2026-09-20 补充）

| 阶段 | 目标 | 设计含义 |
|------|------|---------|
| **阶段一 · 自用** | 先解决自己的问题，跑通「记录 → 规划 → 家长可视化」闭环 | 单用户、本地部署、不做登录 |
| **阶段二 · 可出售给同行** | 项目成熟后作为产品卖给其他独立老师 | 需要用户体系、数据隔离、开箱可用、可平滑升级 |

**核心原则：架构上预留，实现上不做（YAGNI）。** 阶段二的能力现在一律不实现，但**几个"改起来极贵"的不可逆决策必须现在做对** —— 详见 §12。最典型的一条：**所有业务表现在就加 `owner_id` 字段**，现在加一列的成本接近零，将来做多租户时全库改表 + 数据回填的代价极高。

**三个模块的重新定位**（模块编号保持你的原定义不变，变的只是开发顺序）：

| 模块 | 原定位 | 新定位 | 优先级 |
|------|--------|--------|--------|
| ② 学生管理 | 三模块之一 | **系统核心**：记录 + 规划 + 诊断 | ⭐ 最高 |
| ③ 课表课时费 | 三模块之一 | **记录入口**：上完课顺手就记，课时费是副产物 | 高 |
| ① 教材管理 | 三模块之一 | **诊断燃料**：题目 → 知识点 → 作业判分 → 掌握度 | 中（保留现有能力，不急于扩展） |

### 0.1.2 项目定名（2026-09-20 确认）

| 项 | 值 | 说明 |
|---|---|---|
| 中文名 | **拾课** | 「拾起每一节课」；谐音「实课」，与"每节课都记下来"的产品动作同构 |
| 英文标识 | **shike** | 全小写、5 字母、无连字符；用于仓库名 / 包名 / 数据库文件名 / 配置文件名 |
| 释义一句话 | 拾课 —— 把每一节课拾起来 | 对同行介绍时不需要额外解释 |

**为什么是「拾课」而不是「学迹」**：「学迹」更贴"学习轨迹"这个抽象定位，但**「拾课」直接描述了用户每天要做的动作**——上完课，把这一节课记下来。一个面向"解放自己"的工具，名字落在动作上比落在概念上更容易形成习惯记忆；且在商标层面（第 41 类教育服务）「拾课」的占用风险低于各类「学迹 / 学习轨迹」命名。

**命名约束（写代码时须遵守）**：

- 英文标识统一用 `shike`，**不要混用** `Shike` / `SHIKE` / `shike-app` / `shike_app`；出现在代码里的唯一形式是小写 `shike`
- 名字里**不出现**「题库 / 试卷 / Bank / Exam」——定位是学生情况管理，名字不能把自己框回题库工具
- 中文名只在用户可见处出现：页面标题、报告页眉、导出文件名、安装包名

**需同步落实的命名落点**见附录 C.3（共 12 处，Phase 0 一次性做掉）。

### 0.2 核心闭环（一切设计围绕它）

```
排课 ──> 上课 ──> 课后 3 分钟记反馈 ──> 自动沉淀进学生档案
  ↑                      │
  │                      ├──> 更新教学计划进度
  └──────────────────────┴──> 阶段性一键生成家长报告
```

**这个闭环跑通，系统就开始产生价值了。** 题库、组卷、OCR **都不在关键路径上** —— 这是本次定位调整带来的最重要结论。

### 0.3 一句话结论（开源调研）

**三大模块全部建议自建，不引入现成系统底座。** 原因：模块①（题库）虽有成熟开源对标（MathBank ★246、学之思 ★3902），但技术栈/场景不完全贴合且你的雏形已跑通核心链路；模块②（学生管理）和模块③（课表课时费）的开源方案几乎全是「学校/机构 ERP」，对「一对一独立老师」适配度极低。**真正该复用的是组件（KaTeX、pix2tex、FullCalendar）和设计范式（Kimai 的分级费率、MathBank 的组卷排版），不是整套系统。**

同时必须先做一件事：**现有代码是「单体 + 无迁移 + 单页 HTML」结构，直接往上叠两个模块会在两周内失控**，所以路线图的第一步是工程化重构（Phase 0），而非直接写新功能。

## 1. 需求与场景梳理

### 1.1 用户画像与约束

| 维度 | 实际情况 | 对设计的约束 |
|------|---------|-------------|
| 角色 | 一个人 = 老师 + 教务 + 财务 + 客服 | 不需要 RBAC 权限体系；不需要审批流 |
| 定位 | 个人自用工具，**后续可能出售给同行** | 阶段一不做多租户/登录；但架构必须预留（见 §12），否则将来改造要动全库 |
| 用户规模 | 阶段一 1 人 → 阶段二 数十~数百位老师 | 单体架构足够，**不要为规模化提前引入分布式** |
| 学生规模 | 数十人量级，一对一/小班 | 不需要班级/选课/排课算法 |
| 体系 | DSE、A-Level、国内初中、国内高中，且会持续新增 | **体系必须是一等公民**，不能把知识树写死在代码里 |
| 科目 | 目前数学，未来可能扩展 | 学科作为可配置维度，不做硬编码 |
| 使用场景 | 上课时/备课时随手记录，可能平板或手机 | 录入必须快，不能有复杂表单流程 |
| 数据敏感度 | 学生姓名、家长联系方式、收入数据 | 本地优先，不上传第三方（AI 调用需脱敏） |

### 1.2 三大模块需求拆解

**模块① 教材管理**（现状：已实现约 60%）

| 子需求 | 具体场景 | 涉及数据 |
|--------|---------|---------|
| 资料存储 | 电脑里大量教材 PDF、真题卷、讲义、大纲文件需要归档 | 文件 + 体系归属 + 知识点标签 |
| 题目入库 | 从试卷 PDF/Word 拆题 → 打标签 → 入题库 | 题目 + 知识点关联 + 原图 |
| 出卷 | 按知识点/难度/题型选题 → 排版 → 导出可打印试卷 | 组卷规则 + 排版模板 |
| 作业布置 | 从题库挑题发给某个学生 | 作业 + 学生 + 题目 + 判分 |

**模块② 学生管理**（现状：0%）

| 子需求 | 具体场景 | 涉及数据 |
|--------|---------|---------|
| 日常反馈 | 每次课后写几句：表现如何、哪里卡住、作业是什么、下次讲什么 | 反馈记录（挂在课时上） |
| 学生诊断 | 看这个学生的薄弱知识点在哪、最近趋势如何 | 答题记录 + 知识点掌握度聚合 |
| 教学计划 | 这个学生未来 1-2 个月要过哪些知识点、到哪个阶段 | 计划 + 计划项 + 进度 |
| 作业情况 | 布置的作业做了没、错在哪、什么类型的错 | 作业 + 逐题判分 + 错误类型 |
| 后期安排 | 学生学到哪了、什么时候考试、什么时候结课 | 学生状态 + 阶段目标 |

**模块③ 课表记录**（现状：0%）

| 子需求 | 具体场景 | 涉及数据 |
|--------|---------|---------|
| 上课时间 | 谁、什么时候、上多久、线上还是线下 | 课时记录 |
| 课时 | 这个月上了多少节/多少小时 | 课时聚合 |
| 课时费 | 不同学生不同单价，调课/请假/补课怎么算 | 单价快照 + 状态 + 计费规则 |
| 月度计算 | 月底一键算出每个学生应收多少、总收入多少 | 结算单 |

### 1.3 三个隐含的核心矛盾（决定了架构）

1. **多体系并存 vs 单一知识树**：现有知识树是「高中数学 120 节点」的硬编码 JSON。而 DSE 和国内高中数学的章节体系完全不同，A-Level 又是另一套。**必须把「体系」抽成实体，知识树挂在体系下**，否则每加一个体系就要改代码。
2. **模块间信息互通 vs 模块自治**：你明确要求"不同模块之间可以信息互通"。这不是微服务场景（一个人用，别搞微服务），而是**共享数据内核 + 外键关联**：一节课（模块③）关联一个学生（模块②），课上讲了哪些知识点（模块①），课后反馈（模块②）挂在课上，月底这张课自动进入课时费结算（模块③）。**Lesson 是连接三大模块的枢纽实体。**
3. **快速录入 vs 数据规范**：上课时记反馈要快，但学情诊断需要结构化数据。**方案：反馈用自由文本 + 可选结构化标签（错误类型），诊断靠作业判分的结构化数据，不强迫老师每次填长表单。**

**关于 MathBank 的深度说明**（这是本次调研最有价值的发现）：

它是目前 GitHub 上与你需求最接近的项目，且**技术路线几乎一致**（Python + FastAPI + 不用构建工具的前端），但成熟度高一个数量级（7.6MB 仓库 vs 你的 183KB）。它的「多教材大纲一键切换」正是你需要的多体系能力，「一键组卷 + A4 仿真排版 + PDF 导出」正是你模块①缺失的最后一环。

**但为什么仍不建议直接引入**：
- 它是 **AGPL-3.0**。自用无影响（AGPL 只在「向他人提供服务」时触发开源义务），但意味着**你不能直接拷代码进闭源项目后对外分发**；且它的知识树只覆盖**国内高中数学四套教材**，完全没有 DSE / A-Level。
- 它是**纯题库+组卷工具**，没有学生管理、没有课表课时费——恰好是你最缺的两个模块。
- 它的数据模型是自己一套，直接引入会导致你的题库数据被它的结构绑死。

**正确姿势：把它当"设计参考书"**。具体可借鉴的三点：① 多教材大纲的「体系 → 目录树 → 自动映射」数据结构；② 试卷拆题的双策略分流（原生文字提取优先、VLM OCR 降级兜底）；③ A4 仿真排版画布的实现思路。**若你未来想省掉「组卷排版」这块的开发量，可以考虑把它作为独立工具并行使用（导入导出 JSON 互通），而不是把它嵌进来。**

**模块① 结论**：自建为主。现有雏形已跑通「PDF 视觉分割 + Word 分块 + 知识点打标」的核心链路，这是你相对开源项目最独特的部分（视觉分割交互）。缺的是「多体系知识树 + 组卷导出」，补这两块即可。

**关键判断**：开源生态里，「一对一独立老师的学情管理」**基本是空白**。学校/机构系统（Gibbon、RosarioSIS、openSIS、Fedena）全部围绕「多角色 + 班级 + 选课 + 考勤」的批量运营设计，你一个人用不上其中 80% 的功能，而剩下的 20% 还都是 PHP/Ruby 栈。真正贴近场景的（Vellor、Tutor HQ）都是**零 Star 的课程作业级项目**，要么没后端、要么停更。

→ **模块② 结论：必须自建。** 学情诊断的算法可参考 Edulytics 与 Moodle Analytics 的思路（成绩趋势 + 知识点掌握度聚合），家长报告可参考 Tuition-Management-System 的 PDF 生成流程。

**关键判断**：**排课 ≠ 课时费**。开源排课引擎（FET、UniTime、Timefold）解决的是「多班级多教师多教室的约束求解」，而你的需求是「记录已经约定好的课」——这是一个纯粹的 CRUD + 聚合问题，用算法引擎是杀鸡用牛刀。

课时费的本质极简：**上课记录（学生, 时间, 时长, 单价, 状态） → 按月按学生分组求和**。数百行代码即可覆盖调课、请假补课、跨月结算、导出，远比重部署一套 Laravel 全家桶简单可控。

→ **模块③ 结论：自建轻量模块 + 复用 FullCalendar 做 UI + 借鉴 Kimai 的费率模型。**

### 2.5 选型决策总表

| 能力 | 决策 | 依据 |
|------|------|------|
| 系统底座 | **自建** | 三大模块无一个适配独立老师场景 |
| 公式渲染 | 复用 KaTeX（已用） | 成熟、快 |
| 公式 OCR | 复用 pix2tex / LaTeX-OCR | ★16.5k，MIT，本地可跑 |

### 3.3 扩展障碍（按严重度排序）

1. **单文件巨石**：所有路由、DB 操作、模型挤在 `main.py`，再加两个模块必然失控。
2. **无迁移机制**：新增表要手改 `init_db()`，而 `try/except ALTER` 的容错写法会**静默吞掉真实错误**（schema 漂移风险）。
3. **无分层 / 无依赖注入**：每处 `get_db()` 手动 connect/commit/close，容易漏 close。
4. **SQLite 并发**：默认无 WAL；课表与结算涉及较多写操作，需显式开启 `journal_mode=WAL`。
5. **前端无路由**：单 `createApp` + 巨型 state 无法承载多页面；Element Plus/KaTeX 未锁版本，升级有风险。
6. **无用户主体**：学生、课表理应归属某位老师，当前零账号体系（单人自用可接受，但要留扩展位）。
7. **多体系硬编码**：知识树是单个 JSON 文件，加体系需改代码。

### 4.3 模块划分与边界

| 模块 | 职责 | 对外暴露的实体 | 依赖 |
|------|------|--------------|------|
| **M1 教材/题库** | 资料归档、题目入库、多体系知识树、组卷导出 | `Question`、`Node`、`Resource`、`Paper` | 无（最底层） |
| **M2 学生管理** | 学生档案、课后反馈、教学计划、作业判分、学情诊断 | `Student`、`Feedback`、`Plan`、`Assignment` | 依赖 M1（题目）、M3（课时） |
| **M3 课表/课时费** | 课时记录、日历、请假调课、月度结算 | `Lesson`、`Invoice` | 依赖 M2（学生） |
| **M0 共享内核** | 体系、知识点、附件、通用查询 | `Curriculum`、`Node`、`Attachment` | 被全部模块依赖 |

**依赖方向严格单向**：`M3 → M2 → M1 → M0`。反方向的互通（如 M1 想知道某题被谁做过）通过**服务层聚合查询**实现，而不是让 M1 反向依赖 M3。

### 4.4 共享内核与互通机制

用户明确要求"模块之间信息互通"。**实现方式不是微服务、不是消息队列，而是「共享数据内核 + 外键 + 服务层聚合」**，因为单人自用系统引入分布式复杂度是纯粹的自伤。

三条互通主线：

1. **Lesson 是枢纽实体**：一节课同时携带 `student_id`（→ M2）、`node_ids`（→ M1 讲了哪些知识点）、`amount`（→ M3 计费）。课后反馈、作业布置都挂在 lesson 上。**这一张表就把三大模块串起来了。**
2. **知识点掌握度是聚合视图**：M1 的题目 → 打标到 `Node`；M2 的作业判分记录 `question_id + is_correct + error_type`；按 `node_id` 聚合出「这个学生在这个知识点上的正确率」→ 学情诊断雷达图。**数据源跨 M1/M2，靠服务层算，不落冗余表**（数据量小，实时算足够快）。
3. **课时费是派生产物**：`Lesson` 记录完成即产生应计金额（含单价快照），月度结算单只是 `SUM(lessons WHERE period = X AND billable = 1)` 的快照。**结算单一旦生成就冻结，不再随课时记录变动**——这是财务数据的正确性要求。

### 5.2 核心表 DDL（SQLite 方言）

--   所有业务表统一带 owner_id 字段，自用阶段固定为 1（**不实现任何多租户逻辑**）：
--     curricula / nodes / resources / questions / papers / students / lessons
--     feedbacks / plans / assignments / invoices / ability_dims / reports

| P2 | 后期安排 | 阶段目标、考试倒计时、结课提醒 |

**页面**：`/students`（列表）、`/students/{id}`（详情，含时间轴/诊断/计划/作业四个 Tab）、`/students/{id}/report`

**关键逻辑：知识点掌握度算法**

```
对每个知识点 node：
  items = assignment_items
          JOIN questions q ON ...
          JOIN question_nodes qn ON qn.question_id = q.id AND qn.node_id = node.id
          WHERE assignments.student_id = S
          且 items.is_correct IS NOT NULL

  raw_rate  = SUM(is_correct) / COUNT(items)
  mastery   = Σ(is_correct × qn.weight) / Σ(qn.weight)     ← 主考点权重高于"涉及"
```

**分级阈值**（可配置）：`>=80% 掌握` / `60-80% 待巩固` / `<60% 薄弱`

**错误类型分布**：按 `error_type`（概念不清 / 计算失误 / 审题 / 方法不会 / 空白）统计 → 直接回答"这孩子是笨还是粗心"，这是独立老师最需要的一句话结论。

### 6.3 模块③ 课表与课时费

**功能清单**

| 优先级 | 功能 | 说明 |
|-------|------|------|
| P0 | 课表日历 | FullCalendar 月/周视图，每格显示学生名 + 状态色 |
| P0 | 课时记录 CRUD | 时间、时长、学生、模式（线上/线下）、状态、本次内容、覆盖知识点 |
| P0 | 状态流转 | `scheduled → done / cancelled / leave / moved / makeup` |
| P1 | 请假/调课/补课 | 请假：`billable=0`；调课：改 `start_at` 留痕；补课：新建 `makeup` 记录 |
| P1 | 月度结算 | 选月份 → 按学生分组汇总 → 生成结算单（生成时冻结单价与金额） |
| P1 | 收入看板 | 本月/上月/年度收入、按学生/体系分布 |
| P2 | 导出 | 月度课时费明细 Excel；课表图片/PDF |
| P2 | 提醒 | 今日课程提醒（本地通知 / 企业微信推送） |

**计费规则设计（关键）**

```
单节课应计金额 = rate_unit == 'hour'
                 ? rate × (duration_min / 60)
                 : rate                          ← 按次收费

billable 规则：
  done      → 1（正常上课）
  leave     → 0（请假不计费，但记录留痕）
  cancelled → 0（老师取消）
  makeup    → 1（补课计费）
  moved     → 0（原课时作废，新课时另记一条 done）

rate 快照：创建 lesson 时从 students.hourly_rate 复制一份，
         之后修改学生单价不影响历史课时 —— 这是财务数据的基本要求。
```

**月度结算流程**

```
选择月份 → 拉取该月 billable=1 且 status IN (done, makeup) 且 invoice_id IS NULL 的 lessons
        → 按 student_id 分组 → SUM(amount)
        → 生成 invoices 记录 → 回写 lessons.invoice_id（锁定归属）
        → 已生成的结算单不随课时变更（如需修正，作废重开）
```

**页面**：`/schedule`（日历主视图）、`/schedule/lessons`（列表式课时记录）、`/billing`（月度结算 + 收入统计）

### 6.4 家长可视化报告设计（定位调整后 = 核心功能）

**为什么它能大幅提前**：家长报告的早期数据源是**老师的主观评分**，不必等题库判分闭环。这是定位调整带来的最大设计收益。

**三层数据源（按可用时间排序）**

| 层级 | 数据源 | 可用时间 | 呈现形式 |
|------|--------|---------|---------|
| L1 | 老师主观评分（能力维度 1-5）+ 课后反馈文本 | **立即可用** | 能力雷达图 + 反馈摘要 |
| L2 | 作业判分（知识点掌握度） | 题库打通后 | 知识点进度条 |
| L3 | 大考 / 模考成绩 | 手工录入即可 | 成绩趋势折线 |

**能力维度（2026-09-20 已确认，5 个）**

| 维度 | 判断的是什么 | 打分锚点（1 星 → 5 星） |
|------|------------|---------------------|
| **概念理解** | 听懂了吗 | 需要反复解释 → 能自己复述定义与适用条件 |
| **计算准确** | 算得对吗 | 频繁算错 → 基本无计算失误 |
| **解题规范** | 写得规范吗 | 跳步、无过程 → 步骤完整、逻辑清晰 |
| **做题速度** | 做得快吗 | 明显做不完 → 有富余时间检查 |
| **学习主动性** | 状态对吗 | 被动应付 → 主动提问、自觉订正 |

> 维度存在 `ability_dims` 表（数据驱动），**增删维度只插数据、不改代码**。同行若教物理/化学，可以换一套维度 —— 这是能卖给同行的前提之一。
> 打分成本控制：每节课 5 次点击 ≈ 10 秒。**允许只打部分维度**，其余沿用上次分数，不强制填满。

**报告内容结构**（单页，家长 3 分钟内看完）

1. **本阶段概览**：统计周期、上课节数、覆盖的知识模块
2. **能力表现**：能力维度雷达图（**本次 vs 上次对比** —— 让家长看到"变化"，而不是一张孤立的图）
3. **课堂表现摘要**：从课后反馈里抽取 2-3 条亮点
4. **待改进**：2-3 条具体问题（要具体，"计算跳步导致失分"而不是"还需努力"）
5. **下阶段计划**：接下来要攻的知识点与目标
6. **下次课安排**

**输出形式**：首版做**长图 / 图片**（家长微信直接看，无需下载），PDF 次之。**不做在线链接** —— 避免家长看到不该看的内部备注。

**关键设计原则**

| 原则 | 理由 |
|------|------|
| **必须可编辑再发** | 系统生成草稿 → 老师改措辞 → 发出。**绝不能全自动直发**，说错话的代价远高于省下的几分钟 |
| **默认脱敏** | 不出现分数排名、不出现内部备注（`remark`）；姓名可用"XX 同学" |
| **可追溯** | `reports` 表存快照，几个月后能查到当初发过什么 |
| **手动触发为主** | 想发就发；可选"每 4 节课提醒一次" |

### 6.5 快速记录设计（决定系统生死）

既然定位是"解放自己"，**录入成本就是系统的生命线**。目标：**一节课 3 分钟内记完**。

| 手段 | 说明 |
|------|------|
| **课程驱动录入** | 从课表点某节课直接进入反馈，不用"先选学生再选时间" |
| **语音输入** | 说一段话 → 转文字 → AI 自动拆成「表现 / 问题 / 作业 / 下次」四段（契合你的语音输入习惯） |
| **快捷短语** | 按知识点和常见表现预置短语，点一下就插入（如"计算跳步"、"概念混淆"） |
| **上次内容预填** | 默认带入上节课反馈，只改差异部分 |
| **能力评分极简** | 4-6 个维度，点星星，10 秒完成 |
| **允许不完整** | 只写一句话也能存，之后可补。**不能因为字段必填而卡住记录** |

## 9. 开发计划与里程碑（按新定位重排）

> 排序原则：**先让"学生情况记录 + 规划 + 家长可视化"闭环跑通**，题库与交付能力后置。
> 注意 Phase 1 必须包含「课表的最小可用版本」——因为没有"课"就没有反馈的挂载点，两者是同一件事。

| 阶段 | 内容 | 关键交付 | 完成标志（验收） |
|------|------|---------|----------------|
| **Phase 0** | 工程化重构（见 §8） | 后端分层 + Alembic + WAL + 前端 Vite 迁移 | 原功能无损；新表能通过迁移脚本创建 |
| **Phase 1** | ⭐ **记录闭环** | 学生档案、课表最小版（排课/已完成）、**课后反馈（语音输入 + 快捷短语）**、学生时间轴 | **上完一节课 3 分钟内记完反馈；学生页能按时间回顾全部上课记录** |
| **Phase 2** | 教学规划 | 教学计划 / 计划项（绑知识点）、进度勾选、后期安排与考试倒计时 | 能给学生定 1-2 个月计划，每节课后勾进度，能看出计划与实际覆盖的差距 |
| **Phase 3** | ⭐ **家长可视化** | 能力维度评分（1-5）、报告生成（能力雷达**对比**图 + 长图导出）、报告历史 | **一键生成一份家长看得懂、看得出变化的报告**，且发出前可编辑 |
| **Phase 4** | 课表完善与课时费 | 日历视图、请假/调课/补课、月度结算、收入看板 | 月底一键算出每个学生应收金额与总收入 |
| **Phase 5** | 题库与诊断打通 | 多体系知识树、题库筛选页、作业判分、知识点掌握度 | 打开学生页能看到"三角函数 62%，主要错在计算" |
| **Phase 6**（可选） | 教材管理与交付能力 | 资料库、组卷、试卷导出、公式 OCR、AI 辅助 | —— |
| **Phase 7**（可选·商业化） | 出售准备 | 用户体系接入（`owner_id` 从配置换成登录态）、开箱可用（内置模板与示例数据）、一键安装包、授权与版本升级机制 | **一位同行能在 30 分钟内自己装好并用起来** |

> ⚠️ **注意**：Phase 7 之所以能"可选且轻松"，前提是 **§12.1 的 8 条不可逆决策在 Phase 0 就做掉了**。如果那 8 条当时偷懒，Phase 7 就不是"可选项"，而是"返工项"。

**最重要的里程碑判据：Phase 3 结束时，本项目的定位就已经完整实现了** —— 学生规划（Phase 2）、情况记录（Phase 1）、家长可视化（Phase 3）三件事全部闭环。Phase 4-6 属于"顺带把教务和题库也管起来"的扩展，**是加分项而非前提**。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Phase 0 重构工作量大、迟迟不出成果 | 挫败感，半途而废 | 严格限制重构范围：**只分层不重写业务逻辑**，现有录题链路一行不改地搬过去；重构期间新功能冻结 |
| 过度设计（微服务/消息队列/PostgreSQL） | 单人系统背上运维负担 | **明确禁止**：单人自用不引入分布式组件；SQLite 足够，DAO 抽象保留迁移可能即可 |
| 前端从 CDN 改工程化引入构建复杂度 | 开发体验变差 | 用 Vite 官方模板，不额外引入 SSR/微前端；保留单页快速开发的能力 |
| 知识点树数据整理耗时（多体系） | 阻塞 Phase 1 | 首版只做 2 个体系（DSE + 国内高中），各 1-2 个模块的章级树，**先粗后细**；树可随时增补 |
| AGPL 传染风险 | 若将来对外分发有法律问题 | 借鉴 MathBank/gygy-open 的**设计思路与数据结构**，不拷贝其代码；引入第三方库前核对 License |
| 学生/家长数据泄露 | 隐私与合规 | 本地部署不出网；AI 调用前脱敏（不含姓名/联系方式）；家长报告默认不含成绩细节 |
| 课时费算错 | 直接影响收入信任 | 单价快照 + 结算单冻结 + 导出对账明细；结算前提供"预览"步骤 |
| 数据丢失 | 不可逆 | 自动备份 + 一键导出全库 JSON |

## 12. 商业化预留设计（阶段二）

> 前提：**阶段二现在不实现。** 本章的唯一目的是把"改起来极贵"的决策现在做对。
> 判断标准：这件事**现在花 10 分钟、将来能省两周 → 做**；现在要做两天、将来也只要一天 → **不做**。

### 12.1 不可逆决策清单（现在必须做）

| # | 决策 | 现在的做法 | 如果现在不做，将来的代价 |
|---|------|-----------|----------------------|
| 1 | **所有业务表带 `owner_id`** | 加字段，固定值 1；查询统一 `WHERE owner_id = :owner` | 全库改表 + 数据回填 + 改所有查询 + 补隔离测试；**漏一处就是串数据事故** |
| 2 | **不把绝对路径写进数据库** | `file_path` 存相对路径，根目录走配置 | 客户换机器/换盘符后全库路径失效，历史附件全部打不开 |
| 3 | **配置外置** | 端口、数据目录、备份策略、AI Key 全放配置文件/环境变量 | 每来一个客户就要改代码，无法交付 |
| 4 | **PDF 解析做成适配层** | `adapters/pdf.py` 单一出入口（当前实现 PyMuPDF） | 被 AGPL 卡住时必须全项目替换所有调用点 |
| 5 | **知识树/能力维度/反馈模板全部数据驱动** | 都存数据库，代码里不硬编码 | 同行教物理/化学/英语，体系与模板都不同，硬编码 = 无法复用 |
| 6 | **一键全库导出** | "导出全部数据为 JSON + 附件打包" | 客户要迁移、要信任，拿不出数据就卖不动 |
| 7 | **依赖许可清单** | Phase 0 顺手产出 `LICENSES.md` | 出售前才发现踩了 AGPL，返工成本极高 |
| 8 | **数据库迁移机制（Alembic）** | Phase 0 就上 | 客户已存半年数据要升级版本时，没有迁移 = 不敢发版 |

> 这 8 条加起来在 Phase 0 增加的工作量很小（主要在 0.1/0.2 里顺带完成），但每一条都是"现在一列、将来全库"的量级差异。

### 12.2 明确"现在不做"（YAGNI）

| 不做 | 理由 |
|------|------|
| 注册登录、密码体系、找回密码 | 阶段一是单用户；有 `owner_id` 就够 |
| 多租户隔离逻辑、租户管理后台 | 没有客户之前做这个纯属浪费 |
| 订阅计费、支付、试用期 | 商业模式还没定 |
| 家长 / 学生端账号 | 阶段一由你代发报告；要卖时再评估 |
| **微服务 / K8s / 消息队列** | **永远不做**，这个场景不需要 |
| 完整 SaaS 运维（监控、告警、限流、CDN） | 阶段二再谈 |

### 12.3 阶段二的商业模式选项

| 形态 | 优点 | 缺点 | 适合度 |
|------|------|------|--------|
| **本地部署 + 授权码** | 学生数据不出客户电脑（**对同行是强卖点**）；你不承担运维与数据安全责任 | 要处理分发、升级、防拷贝；客户可能装不上 | ⭐ 与产品气质最契合 |
| **SaaS 订阅** | 客户零安装、升级即时、收入可持续 | 你要运维服务器、做备份、承担个人信息保护责任；同行可能担心学生数据上传 | 中期可考虑 |
| 一次性买断 + 交付源码 | 交付简单 | 容易被二次分发 | 不推荐 |

**建议路径**：阶段一自用跑顺 → 找 2-3 位同行免费试用（此时**故意不做登录**，正好验证"单人单机"形态够不够用）→ 再决定形态。

### 12.4 卖点判断（很重要）

**你卖的不会是"题库功能"。** MathBank 免费且开源，题库这块没有付费空间。差异化在**「学生情况记录 + 教学规划 + 家长报告」这条链**，尤其是：

- **家长报告的呈现质量**（家长看得懂、看得出变化）—— 这是同行最痛、也最难自己做的部分
- **多体系支持**（DSE / A-Level / 国内），多数同类工具只覆盖国内高考
- **数据本地化**（隐私卖点）

### 12.5 合规提醒（涉及未成年人数据）

一旦出售，你就是"个人信息处理者"。学生是**未成年人**，家长联系方式属个人信息：

- 需有隐私说明与用户授权流程
- **数据默认存客户本地**（选本地部署可大幅降低合规负担）
- 若走 SaaS：最小化采集、加密传输、支持删除、不出境
- AI 功能（语音转文字、AI 拆段）调用第三方前必须**脱敏**（不含姓名、联系方式）

> 本章不需要在阶段一投入实现精力，但 **12.1 的 8 条要在 Phase 0 顺手做掉**。

### C.4 GitHub 仓库改名前置检查（2026-09-20 实测通过）

| 检查项 | 实测结果 | 改名影响 |
|---|---|---|
| 可见性 | public | 保持 public |
| 提交数 | 1 | 全部保留，不产生复制 |
| Stars / Forks | 0 / 0 | 无外部依赖引用旧路径 |
| GitHub Pages | **未启用**（API 返回 404） | Pages 是唯一**不重定向**的项，未用 → 无风险 |
| Actions workflows | **无**（`.github/workflows` 不存在） | 无硬编码仓库名需修改 |
| Issues | 已启用、无内容 | 保留 |
| 分支 / 默认分支 | `main` | 保留 |

**改名机制说明**：GitHub 改名是**原地重命名**（非复制），提交历史、分支、设置、issue、secrets 全部保留，且**可随时改回**。旧 URL（网页 + `git clone`/`push`/`pull`）自动 301 永久重定向。

**唯一注意**：改名后若在**同一账号下**新建一个叫 `question-bank` 的仓库，旧链接的重定向会失效并指向新仓库。当前无此需求。

**改名后需手动做的两件事**：

```bash
# 1. 本地 remote 同步（不改也能推拉，但 gh 默认仓库会指向旧名，迟早踩坑）
git remote set-url origin https://github.com/ILearn-better/shike.git

# 2. 验证
git remote -v && gh repo view ILearn-better/shike --json name,url
```
