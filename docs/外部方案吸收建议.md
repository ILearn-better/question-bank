> 输入：三篇腾讯文档

> ③ 《AI学习重点_试卷题库项目对比表》
>
> 对照物：本仓库（question-bank / 拾课）当前实际代码状态（2026-10-03 实测）
> 结论定位：哪些吸收、哪些我们反而对、怎么落

## 0. 一句话结论

对方方案的**技术路线和我们同源**（都用题号规则切题，不靠模型切题），
真正的差距不在"切题能力"，而在**元数据与协议化**——
他们有 `confidence` / `flags` / `fingerprint` 和一份 Import Contract，我们这四样**一个都没有**（已实测确认）。

但**不能照搬**：他们的模型是"机器全量拆 → 事后逐条审"（审核是独立瓶颈环节），
我们的是"人工切分时同步确认"（确认即入库），后者更适合个人教师。
**吸收他们的元数据与批量入口，保留我们"确认即入库 + 下游闭环"的形态。**

这句话我们**已经做到了一半**（可管理、可组卷），缺的是"可追溯"（fingerprint / 来源链路）和"可审核"（元数据标记）。

## 2. 我们当前的实际状态（实测，非推测）

对 `backend/app` + `frontend` + `alembic/versions` 全量检索的结果：

| 能力 | 对方文档要求 | 我们的实际情况 |
|---|---|---|
| 录题入口 | Import API（批量） | ✅ 已有 3 个入口：PDF 分界线、Word 行标记双线截原貌图、扫描版纯截图 |
| 视觉事实源（原题截图） | 要求保留 | ✅ **已实现**：区域截图 3 倍分辨率、行标记双线截原貌、扫描版纯截图 |
| 自动题号预切 | doc2md 承担 | ✅ **已实现**（正则，样例卷 10/10 命中） |
| `confidence` 置信度 | High/Medium/Low 分级 | ❌ **完全没有**（全库检索无命中） |
| `flags` 异常标记 | answer_inferred / empty_stem / inline_split | ❌ **完全没有** |
| `fingerprint` 查重 | 四层查重 | ❌ **完全没有** |
| Import Contract / JSON Schema | contract/v1.schema.json | ❌ **完全没有** |
| 待审核状态流 | PENDING_REVIEW → APPROVED | ❌ **没有**（且**建议不要照搬**，见 §5.2） |
| 下游闭环 | "复用现有功能"（P1，没做） | ✅ **我们的优势**：出卷、作业、课后反馈、笔记插题、教师版/学生版导出 |

**基础设施我们已经比对方文档描述的更完整**：分层后端 `app/{routers,services,adapters}`、
16 个路由模块、13 个服务、alembic 迁移 0001–0016、零构建前端 + 本地 vendor。
对方文档 ② 里"开工前先做一次仓库盘点"这一步，对我们已经不需要了。

## 3. 核心判断：两条路线不是替代关系

| | 对方的路线 | 我们的路线 |
|---|---|---|
| 触发 | 上传一份试卷文件 | 打开录题页，选一份文档 |
| 节奏 | **批量**：一次性拆完 20–50 页 | **单题**：切一道、录一道 |
| 机器做什么 | 全量识别 + 拆题 + 置信度评估 | 只做**预切**（放好分界线），不做识别 |
| 人工做什么 | 逐条**审核**机器结果 | 切分时**同步确认**（同一个动作） |
| 入库时机 | 审核通过后 | 保存即入库 |
| 之后能干什么 | 只有题库（组卷标 P1 未做） | **立刻**能出卷 / 发作业 / 写反馈 / 插笔记 |

**关键洞察：**

1. **我们的"确认"成本更低。** 对方模型里，"审核"是独立环节——几百道题每道点一遍，
   是纯粹的额外成本。我们的是"划线的同时就已经在看、在确认"，人工确认和录入**共用一个动作**。
   对个人教师（不是流水线工人）来说，我们这种更省力。

2. **他们缺下游，我们缺上游。** 他们的链路终点是"正式题库"，组卷只标了 P1 说"复用现有功能"；
   而我们的库已经连着出卷、作业、反馈、笔记。**批量导入如果不能直接进现有 questions 表并用上这些下游，就只是个更大的数据库。**

3. **所以正确的吸收方式是：把他们上游的"批量 + 元数据"接到我们下游的"闭环"上**，
   而不是在他们的架构上重建一套。

## 4. 值得吸收的（按性价比排序）

### 4.1 【最值钱】题号预切的置信度标记

我们现在的自动预切**已经在做机器判断了，但不输出任何置信度**。
结果是用户看到分界线自动放好了，**不知道哪几根是机器猜的**——这恰恰是对方文档花整节篇幅解决的问题。

**具体做法**（成本极低）：

| 命中形态 | 判定 | 界面表现 |
|---|---|---|
| 行首 `1.` `2、` `3．` | `strong` | 实线（现状） |
| 行首 `（3）` `(3)` `第4题` | `strong` | 实线（现状） |
| 行中出现 `（3）`、行首小数 `1.5`、页码干扰 | `weak` | **橙色虚线** |

再在工具栏加一个「仅看需检查的线」开关。收益：把"不知道哪根是猜的"变成"一眼看到要查哪几根"。

> 这一步**不需要引入任何模型**，就是在现有预切函数返回值里多加一个 `level` 字段。

### 4.2 【最值钱】题干指纹查重（只做 Level 1 + Level 2）

文档 ① 设计了四层查重。对我们来说，**前两层就够，后两层不必做**：

| 层级 | 内容 | 我们要不要 |
|---|---|---|
| L1 Exact fingerprint | 题干+选项完全一致 | ✅ 要 |
| L2 Normalized fingerprint | 去空格/标点/格式差异 | ✅ 要（LaTeX 也要归一） |
| L3 Embedding 相似度 | 语义相似 | ❌ 量级不够，先不做 |
| L4 LLM 语义判断 | 区分重复/变式 | ❌ 先不做 |

**为什么这对我们比对对方更重要：** 我们有**三个入口**混录题库，同一道题从 PDF 划一遍、
又从 Word 录一遍的概率很高。而且文档 ② 提到他们已有的真实样本
（宝安七上期中卷、2021 深圳中考卷）说明题库会持续长大——**越晚做查重，历史脏数据越难清**。

**具体做法**：保存前用归一化题干算 hash → 查库 → 命中则提示
「疑似与已有第 N 题重复（来源：xxx），仍要录入吗？」，允许强制录入。

### 4.3 入口统一 DTO（内部 Import Contract）

**问题**：我们现在三个入口各自直接写 `questions` 表，没有中间层。
将来每接一个新入口（OCR、doc2md、手机拍照），都要再写一套入库逻辑。

**做法**：定义一个内部 DTO，所有入口先产出 DTO 再统一入库。关键字段：

```
origin:   manual | rule_preseg | crop | ocr | doc2md   ← 来源可追溯
source:   { document_id, page, block_range, crop_rect } ← 回溯到原始位置
quality:  { confidence, flags, fingerprint }            ← 4.1 / 4.2 的落点
```

**但要克制**：文档 ② 要求产出独立的 `contract/v1.schema.json` 对外发布。
**我们现在不需要那个 JSON Schema 文件**——它存在的理由是"跨项目边界"（doc2md → question-bank），
而我们目前没有跨项目消费者。等真的接 doc2md 那天再抽 schema，不要提前仪式化。

> 这条改动会碰到现有入库路径，**必须按"只加不改"来**：新增 DTO 层，现有入口内部改走 DTO，
> 对外行为（接口、界面、数据）不变。

### 4.4 数据备份 / 恢复入口

文档 ② 把"数据安全"列为第一条铁律，并且代码里有对应的真实约束：
`config.py` 的注释写着「配置外置：全部环境变量统一 SHIKE_ 前缀，便于将来交付给同行时改配置不改代码」——
说明这个项目以后是要**交给别人用的**。

而现状是：**题库数据只有 `backend/shike.db` 一份**（用户还明确要求不把它同步到 git）。
一次误操作就是不可逆的。

**做法**：复用已有的 `notes_transfer`（笔记 zip 备份迁移）思路，
做「一键导出题库备份 / 从备份恢复」。成本中低，风险收益比很高。

### 4.5 内化文档 ② 的开发纪律

文档 ② 的"铁律"部分其实是**为 AI 协作开发写的规范**，几条我们直接可用：

| 纪律 | 我们的现状 | 建议 |
|---|---|---|
| **只加不改**（additive-only） | 我们实际在"改"（加分界线时改了内容块视图） | 写进 `DEVELOPMENT.md`，动现有代码先说明影响面 |
| 每个功能一个可回滚提交 | ✅ 已经在做（commit 粒度合理） | 保持 |
| 表结构变更必须写迁移 + 备份说明 | ⚠️ 迁移有（alembic 0016 个），**备份说明没有** | 每个含迁移的功能附一句"升级注意事项" |
| 不引入代码级依赖，以文件为边界 | ✅ 天然符合（没 import 过 doc2md） | 明确写下来，防止将来偷懒 |
| 生产实例零影响 / 用数据副本开发 | ⚠️ 只有一份库，没有副本概念 | 配合 4.4 |

### 4.6 按卷种分策略的题号正则

三份文档反复出现 **A-Level / DSE / Cambridge / Further Mathematics** 字样，
说明另一条线的真实场景是**国际课程试卷**。英文卷的题号形态和中文卷完全不同：

| 卷种 | 题号形态 | 版面特点 | 我们现在的正则 |
|---|---|---|---|
| 中文卷（我们已覆盖） | `1.` `2、` `（3）` `第4题` | 单栏为主 | ✅ 已适配 |
| A-Level / DSE 英文卷 | `1` `(a)` `(i)` `Question 1` | **双栏**、公式极密、频繁跨页 | ❌ 未适配 |

**做法**：正则改成**按卷种分档**（一个 `profile` 参数），不要用一套正则硬吃所有卷。
顺带一提：双栏卷的"阅读顺序"问题，我们现在的按行 y 坐标排序会串栏——
这是接英文卷之前必须解决的。**优先级取决于你是否真的要处理国际课程卷。**

## 5. 我们反而做对的地方（防止照搬）

### 5.1 我们已经有"视觉事实源"，这是最硬的资产

文档 ① 用整节篇幅论证"保留原题截图作为视觉事实源"，
文档 ② 甚至明确"图片型试卷本期只存原图不自动拆题"（V1.5 放弃）。

而我们**三样都已经做完了**：PDF 区域截图（3 倍分辨率，打印不糊）、
Word 行标记双线截原貌图、扫描版纯截图。他们那条路要"从零建截图管线"，
我们是"直接复用现有截图管线"。

### 5.2 不要照搬 PENDING_REVIEW → APPROVED 双表结构

这是最重要的一条"不要照搬"。

| | 对方设计 | 我们的情况 |
|---|---|---|
| 待审状态 | 独立表 / 独立状态，`PENDING_REVIEW` | 无 |
| 审核动作 | 专门跑到审核工作台，逐条点 | 就是录题时的保存动作 |
| 适合 | **一次导入几百道题**的批量场景 | **日常备课录几道**的场景 |

如果把"待审核"变成**所有题目**的必经状态，我们就凭空多出一个"待审核积压"的中间态，
而用户是个人教师——积压会变成心理负担，且不产生任何价值。

**正确做法**：**只在批量导入路径（doc2md / OCR）上引入待审核队列**，
手动录题路径保持"确认即入库"。也就是把状态流做成**入口相关**，而不是全局强制。

### 5.3 技术选型上我们已经更清醒

我们的 `docs/版面识别方案调研.md`（2026-09-24）已经把这几件事想清楚并落地了：

- **"版面分析 ≠ 题目切分"**——通用模型标签里根本没有"题目"（对方文档没点破这一层）
- **"不要用模型切题"**——先把文本层用尽
- **"先把自动预切 + 人工确认做出来，比引入任何模型都值钱"**——且**已经实现**

对方文档 ① 里 doc2md 承担的也是**规则切题**（题号正则），和我们是同源路线。
所以**不是"要不要换成他们的方式"，而是"在我们已经建好的预切上补元数据"**。

## 6. 落地路线

### P0 — 立刻做（1–2 天，不动现有架构）

| # | 事项 | 落点 | 为什么先做 |
|---|---|---|---|
| 1 | 预切置信度标记（strong / weak） | 后端预切函数返回值 + 前端线的样式 | 纯增量，不动任何现有行为；直接解决"不知道哪根是猜的" |
| 2 | 题干指纹查重（L1+L2） | 保存题目前插一次查重 + 提示 | 越晚做历史脏数据越难清；三个入口混录必然产生重复 |

### P1 — 紧接着（3–5 天）

| # | 事项 | 注意 |
|---|---|---|
| 3 | 入口统一 DTO（带 origin / source / quality） | **只加不改**：新增 DTO 层，对外行为不变 |
| 4 | 题库备份 / 恢复入口 | 复用 `notes_transfer` 的 zip 思路 |
| 5 | 写一份 `DEVELOPMENT.md`（内化文档 ② 的纪律） | 纯文档，零风险 |

### P2 — 按需，不主动做

| # | 事项 | 触发条件 |
|---|---|---|
| 6 | doc2md 适配器（文件为边界，透传 confidence/flags/fingerprint，失败进错误清单不丢弃） | **真的要用 doc2md 时**才做，此时才需要待审核队列 |
| 7 | 按卷种分策略的题号正则（含双栏阅读顺序） | 真的要处理 A-Level / DSE 英文卷时 |

### 明确不做（和已有判断一致）

- ❌ **不引入全局待审核积压队列**（个人教师场景下是负担，见 §5.2）
- ❌ **不做 L3/L4 语义查重**（embedding / LLM）——量级不够，L1/L2 足够
- ❌ **不做全自动拆题**——反对"一开始就追求 100% 自动化而取消人工审核"（文档 ① 自己也这么写）
- ❌ 排行榜 / AI 老师全套 / 复杂权限体系（文档 ① §12 自己也列为暂缓）
- ❌ **不立刻抽 `contract/v1.schema.json`** 对外发布——没有跨项目消费者前是仪式化成本

## 7. 需要你确认的问题

1. **英文卷（A-Level / DSE）在你的真实使用范围内吗？**
   这直接决定 4.6（按卷种分正则 + 双栏阅读顺序）做不做，以及要不要导入他们的样本。

2. **"批量导入历史卷子"这件事你真的需要吗？**
   如果需要（比如手上压着一批没数字化的旧卷），那 P2 的 doc2md 适配器 + 待审核队列值得提前到 P1。
   如果不需要（日常都是新卷随用随录），那 §5.2 的判断就成立，我们可以完全不碰待审核体系。

3. **题库备份要不要现在就做？** 现在只有一份 `shike.db`，且用户明确要求不进 git。

4. **一个数据核对项**：文档 ② 说"`data/` 存题库数据"，而我们实机是 `backend/shike.db`
   （可由 `SHIKE_DB_PATH` 覆盖）。请确认生产机上的实际路径，避免升级流程写错备份对象。
