## 一、三个 skill 的最终边界

| skill | 一句话 | 关键入口 | 不需要服务？ |
|---|---|---|---|
| `shike-ingest` | 文件 → 题库题目（识别 + 修图 + 入库 + 待人工报告） | `auto_import_cli.py` / `POST /api/auto/import-path` | 需要 |
| `shike-paper` | 检索 → 人确认 → 组卷导出 html/docx/pdf | `GET /api/questions/search` → `GET /api/papers/export` | 需要 |
| `shike-doc` | 文件 → Markdown（看 / 存 .md / 存笔记） | 本地 `doc_to_note.to_markdown()`；`POST /api/notes/import-doc` | 路 A 不需要 |

分界线只有一句：**「要不要变成能出卷的题」**。要 → ingest；只是文字 → doc；已有题要排版 → paper。

## 二、草案里写错 / 写漏的地方（重点）

### 1. 退出码 0 不代表成功 —— 最要紧的一条

草案写「按退出码 0/2/1 分别报告」。实测：**整页识别失败时任务状态是 `partial`，CLI 仍返回 0**。

```
（临库、无 AI 配置、1 页扫描件）
CLI 输出：结果：共 1 条 → 已入库 0，待人工 0，跳过 1
         跳过的 1 条（模型这页确实没读出题）：no_content×1
EXIT=0
真相：jobs[0] = {"status":"failed","failed":1,"error":"整批识别都失败了，请检查 AI 配置或网络"}
```

原因：`auto_import_cli.py:231-233` 只判 `status=="failed"` 才返回 1，`partial` 落到「看 needs_human」那支；
而整批失败时条目是 `skip` 不是 `needs_human`，于是 0。
更糟的是 `skipped` 的固定文案「模型这页确实没读出题」——把「AI 挂了」说成「这页没题」。

→ skill 里改成三条并列判据：`counts.approved` + `progress.pages_done == total_pages` + `report.failed_pages/jobs`。

### 2. `resume` 会把任务"洗成"成功

草案说「resume 收尾入库」。实测 `resume` **无条件**写 `status="done"`、`ok=true`、`stage="完成"`，
且 `build_report` 里没有 `failed_pages` 字段（只有 `run_task` 才补），所以：

```
resume 前：status=partial  ok=false  report.failed_pages=[{...}]  progress 0/1
resume 后：status=done     ok=true   report 无 failed_pages      progress 0/1   jobs[0].status=failed
```

→ skill 要求：`failed_pages` 必须在 resume **之前**记下；resume 之后只能靠 `jobs[].status` 和
`progress.pages_done` 判断是否干净。

### 3. `report.next` 不可信

同一场景，`next` = 「全部处理完，0 条已入库。」——明明有一页整页失败。它只判 `needs_human` 是否为空。
→ skill 不用 `next` 作为结论，只作为附注。

### 4. 组卷**没有**自动选题能力（草案漏了一步）

草案把 `shike-paper` 的后端写成「`GET /api/questions/search` → `GET /api/papers/export?ids=…`」，
但没写明**这一步是必做的编排**：`papers.py` 只吃 `ids` 字符串（≤200），服务端不知道"导数"是什么，
`grep 组卷 app/routers app/services` 无任何自动选题实现。
→ skill 把流程钉死为「检索 → 给人确认 → 按卷面顺序排 ids → 导出」，并写明题量不够时如实说。

### 5. 带分区模板会让题号乱序（草案完全没提）

`paper_style.layout()` 按 `sections[].qtypes/difficulties` 把题目**重新聚合**，
而题号 `n` 是导出时按 `ids` 顺序编的。两者不一致时：

```
ids = [解答题, 选择题, 填空题]（即 n=1,2,3），模板 template_id=1
渲染结果：一、选择题 → 2.   二、填空题 → 3.   三、解答题 → 1.
```

导出成功、不报错、看着像卷子。内置四套模板**全都带分区**。
→ skill 要求：套模板时 ids 必须先按分区顺序（选择→填空→解答）排好；不套模板才原样印。

> ⚠️ **这条要求已被 R5 取代**：现在服务端在 `layout()` 里按最终渲染顺序跨分区连续重编 `1..N`，
> 调用方**不必**预分组（分区内的先后仍由 ids 顺序决定）。见「四之二」第 5 条。

### 6. 「电子版 PDF 的文字层对公式是废的」—— **这条草案是对的**，且拿到了证据

`doc_to_note.pdf_to_markdown` 只做 `page.get_text()`，没有任何公式重建：

```
已知集合 -> "\uf07b \uf07d 9 U x x \uf03d 是小于的正整数"   （PUA 字符：Symbol 字体映射丢失）
根号/分数 -> 内容顺序错乱
```

Word 走 OMML 分支也只取 `w:m:t` 的文字形式（源码注释明说「反向 XSLT 没做」）。
→ skill 写明：要公式必须走 `shike-ingest`（视觉模型提示词要求输出 `$…$` / `$$…$$`），或人工校。

### 7. 端口判定比草案复杂：有两套规则并存

- `auto_import_cli.py:49-61`、各 `test_*.py`：`SHIKE_BASE` 优先，否则**仓库根目录名**含
  `question-bank-ai` → 8010，否则 8000。（注意是根目录名，不是 `backend`）
- `启动拾课.bat`：`SHIKE_PORT`（默认 8000），**完全不看目录名**。

→ 两套可能打架（在 `question-bank-ai` 里用 bat 起服务、没设 `SHIKE_PORT`，服务在 8000 而 CLI 去连 8010）。
→ skill 改成「**探到哪个用哪个**」：`SHIKE_BASE` → 8000 → 8010，逐个 `GET /api/auto/curricula` 试，2 秒超时。

### 8. `http_proxy` 的表现形态比预期更坑

草案只说「urllib 探 127.0.0.1 会 502」。实测 CLI 自己（`urllib.request.urlopen`，没绕代理）在服务**没起**时：

```
HTTP 502 /api/auto/curricula：Bad Gateway      ← 看着像服务挂了
EXIT=1
清空代理后才是真话：
连不上服务（http://127.0.0.1:8000）：[WinError 10061] 由于目标计算机积极拒绝，无法连接。
```

→ skill 把「502 = 先清代理」写成独立一行失败路径，并在所有调用示例前清 `http_proxy/https_proxy`。

### 9. 页范围写法错 → **500**，不是 422

`routers/auto.py::_precheck_pages` 里 `parse_pages()` 在 `try` 之外，
`ValueError("页范围写法认不出")` 直接冒到全局处理器：

```
POST /api/auto/import-path {"pages":"三到五"}  →  500
{"detail":"服务端出错：ValueError: 页范围写法认不出：'三到五'（支持 1-30,35 或 all）"}
```

→ skill 单独列一条「收到 500 且含『页范围写法认不出』= 参数问题，不是服务故障」。

## 四、发现的接口缺陷（不在本轮修复范围，建议下一轮处理）

> ⚠️ 本节保留**发现当时**的原始记录，不作修改。这 6 条已在同一轮修掉，
> 见下面的「四之二、同轮已修复」。

1. **`partial` 被 CLI 报成退出码 0**（`auto_import_cli.py:231-233`）—— 自动化会把「有页失败」当成功。
2. **`resume` 无条件写 `done/ok=true`**（`auto_import.py:571`）且不重算 `failed_pages` —— 会覆盖掉真实状态。
3. **`report.next` 只看 `needs_human`**（`auto_import.py:283-288`）—— 有页失败时仍说「全部处理完」。
4. **页范围写法错由 `ValueError` 冒成 500**（`routers/auto.py:96` 在 `try` 之外）—— 应是 422。
5. **带分区模板的题号乱序**（`paper_style.layout` + `paper_export` 的 `it["n"]`）——
   要么导出时按分区重新编号，要么在 `sections` 使用时提示调用方先分组。现状是静默出错。
6. `report.status` 写在报告里的是**写报告那一刻**的值（`approving`），与任务最终 `status` 不一致（小瑕疵）。

前 4 条都属于「静默给出错误结论」，与 R2 那次「先删旧结果」是同一类问题：
不是崩，是让人以为成功。

## 四之二、同轮已修复（R5 / R6）

上面 6 条在这一轮都动了。第三列是**回归绿之后**才填的（`test_auto_import_contract.py` **41 项** /
`test_paper_layout.py` 20 项，均为 exit=0）。

| # | 哪条 | 改成什么 | 用什么验的 |
|---|---|---|---|
| 1 | `partial` 被 CLI 报成退出码 0 | 判据收敛到 `auto_import_cli.exit_code_of()` **一处**，三处调用点（上传、`--status`、`--resume`）共用；新增码 **3** 表示「有页没识别成」，优先级 `1 > 3 > 2 > 0` | `test_auto_import_contract` 的 `CASES` **8 例**（含「页失败压过 needs_human」「`report=None` 时靠 `jobs[].failed`」）+ **skill-smith 的 12 组 CLI 接线**（`--status`/`--resume`/主流程 × 4 档，打桩真调 `main()`）；**含负对照**：把 `exit_code_of` 换成恒返回 99 → 11 组翻号，只有走 `_wait` 超时那组不经过它 |
| 2 | `resume` 无条件写 `done/ok=true` | `resume` 重算 `_failed_pages()`，按 `"partial" if failed else "done"` 落状态，再用**新状态**重建报告（不再洗掉页失败） | 同文件两处：①`run_task` / `resume` 都要有 `task.status` 赋值 + `build_report(` 调用（位置断言，防漏一处）；②**反面断言**「`resume` 里没有无条件 `task.status = "done"/"partial"`」（只挡终态，不挡 `"fixing"` 中间态） |
| 3 | `report.next` 只看 `needs_human` | 页数改成 **`pages_lost` = Σ(`pages_total` − `done`)**，在 `build_report` 里**只算一次**，`next` 与 CLI 摘要都读它；`next` 按 `pages_lost` 分两种措辞（有缺页 / `== 0` 时「整批没跑成」）。原先按 `failed` 求和会报小 —— 整批没跑成那批 `failed` 恒为 0 | 同文件三条：`report` 带 `failed_pages`、`next` 点出「没识别成」、`next` **不含**「全部处理完」。`pages_lost` 的数值另由 **③b 三条**钉住（**必须两批合并才测得出来**，单批时新旧算法同结果）：`pages_lost == 4`（`Σ(pages_total−done)`；旧算法 `Σ(failed)` 会得 2）、`next` 里也念「共 4 页」（页数只有一处出处）、两参调用 `pages_lost == 0`（只断言「键存在且等于 0」，挡 `pages_lost or None` 那类回退）。tester 还做过**破坏性复验**：把算法改回 `sum(failed)` → 两条红（得 2 / `next` 不含 4），复原后 sha256 逐字一致、41 项全绿。输出层另由 **4 条**钉住 `_print_report` 的「不印偏小的数」：旧任务报告（有 `failed_pages`、缺 `pages_lost` 键）→ 印「页数不详」且**不**印任何页数；`pages_lost = 0` → 印「共 0 页」而不落进「页数不详」（守 `is None` vs `x or 兜底`） |
| 4 | 页范围 `ValueError` 冒成 500 | `_precheck_pages` 把 `parse_pages` 包进 `try`，`except ValueError` → **422**，文案 `页范围写法认不出：…（支持 1-30,35 或 all）` | 同文件 `_precheck_pages` 三条：写法认不出 → 422、正常 `1-3` → `[1,2,3]`（正面对照，别把整条路径都改成 422）、越界 → 422 |
| 5 | 带分区模板题号乱序 | `paper_style.layout()` 返回前按**最终渲染顺序跨分区连续重编** `n = 1..N`（造新 dict，不污染调用方）；`flat()` 复用 `layout()`，卷面与答案区同源 | `test_paper_layout` 的 **E**（正文编号从 1 起连续、答案区与正文**逐位相等**、E2 入参 `6,7,8` 也得重编成 `1,2,3` 且配对正确、入参不被污染）+ **F**（无 `sections` 时两边一致且都是原号） |
| 6 | `report.status` 是写报告那一刻的中间值 | 两处（`run_task` / `resume`）都改成**先定 status 再 `build_report`**，报告里的 `status` 与任务终态一致（`done` / `partial`） | 同文件：`build_report` 只把 `task.status` 抄进报告、不做修正（用 `"approving"` 打进去，报告里就得是 `"approving"`）—— 因此「谁先谁后」必须由上面的位置断言守 |

同轮还带出两条同源改动，一并记在这里：

- **`approved == 0` 且 `needs_human == 0` → 码 1**（新增档，排在码 3 之前）。
  典型场景是 30 页全跑完、`failed=0`，但模型全判成 `no_content`，`skipped=30` ——
  没有这一档就会落到 `return 0`，对用户说「全部入库，没有遗留」，而一条都没入库。
  验法：`test_auto_import_contract` 的 `CASES` 第 7 例（`approved=0` 且无待审 → 必须 1）。
- **`failed_pages[]` 补齐字段**：从只带 `job_id` + `error` 变成
  `{job_id, error, done, failed, pages_total}`，`failed` 是**页数**。
  根因是 `_failed_pages` 原先只判 `job.error and not job.done`，
  而「一批里部分页挂了」时 `batch_page._finalize` 走 else 分支、`error` 保持 `None`，
  于是整批被漏掉、报告说「全部完成」。
  验法：同文件 **三探针** —— A（`done=28/failed=2/error=None`，真实形态，必须报 1 条且带 `failed=2`、`pages_total=30`）、
